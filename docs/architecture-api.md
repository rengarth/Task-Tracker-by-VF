# Архитектура и контракт API

## Чек-лист v3

Миграция V3 объединяет несколько списков одной задачи и вводит отложенное UNIQUE(task_id). `checklists/save` отклоняет второй список, фиксирует заголовок «Чек-лист». При импорте старых резервных копий списки нормализуются перед записью. `checklist-items/reorder`: `{checklistId, ids: [uuid,...]}` с общей revision; требуется полный набор ID данного списка без повторов. Изменение порядка атомарно. Отмена удаления использует `checklist-items/save` с прежним ID и значениями. Клиент держит историю отмены в карточке, не в базе.

## Шаблоны и история изменений v4

Миграция V4 добавляет `task_templates` и `task_audit`, а также два стартовых шаблона монтажа. `templates/save` и `templates/delete` управляют библиотекой; `tasks/from-template` атомарно создаёт задачу и собственный чек-лист с новыми ID. Шаблон хранит название, описание, исполнителя, приоритет и тексты пунктов; статус, даты, комментарии, фактическое время и отметки выполнения не копируются. Существующие задачи не зависят от последующих изменений шаблона.

`Audit.record` сравнивает исходное и подтверждённое состояния в той же транзакции, после расширения родителей и проверки конфликтов. Записи относятся к задаче и включают поля, чек-лист, комментарии, фактическое время, таймер и повторения. Отклонённые изменения в журнал не попадают. В JSON-архив входят шаблоны и журнал; старые архивы без этих массивов принимаются с пустой историей. Журнал начинается с миграции V4, прошлые действия задним числом не реконструируются.

## Аналитический XLSX

`GET /api/v1/analytics/export?from=2026-10-12&to=2026-10-18&zone=Europe%2FMoscow` возвращает XLSX-вложение (Cache-Control: no-store). Даты включительны, лимит 3661 день; некорректные границы и часовой пояс дают HTTP 400. Сервис читает один согласованный снимок и один момент времени; экспорт не изменяет БД или таймер. `AnalyticsExport` формирует четыре листа Apache POI с числовыми датами/часами, фильтрами, закреплением заголовков, формулами и рассчитанными кэшированными результатами. Пользовательский текст записывается как строка, не формула. Определения метрик и исключений находятся в README и на первом листе.

## Структура

- `frontend/src/App.tsx`: навигация, календарные виды, фильтры, подтверждения, клиентская история Undo.
- `frontend/src/TaskEditor.tsx`: редактор, дочерние сущности, таймер и повторения.
- `frontend/src/model.ts`: типы, разбиение/раскладка календарных интервалов, вычисление просрочки и рекурсивного факта.
- `backend/.../Model.java`: типизированные модели сущностей и согласованного снимка.
- `Rules.java`: инварианты дерева, расширение предков, конфликты и разбиение по дням.
- `PlannerService.java`: команды, транзакции, таймер, генерация повторений, импорт и статистика.
- `Store.java`: JDBC, блокировка версии, чтение снимка, upsert изменённых записей и удаление отсутствующих ID.
- `Api.java`: HTTP-ресурсы `/api/v1`, унифицированные ошибки.

Сущности разнесены по таблицам `tasks`, `checklists`, `checklist_items`, `comments`, `time_entries`, `recurrences`, `task_templates`, `task_audit`, `planner_meta`. Внешние ключи, календарные timestamps, статус и индексы — SQL-колонки; остальные свойства каждой сущности находятся в её собственной JSONB-записи. Это не единый JSON-документ базы. ID и связи контролируются реляционно. Первая миграция создаёт схему; вторая делает FK дочерних сущностей отложенными до COMMIT для атомарного импорта с заменой связей.

Любая мутация берёт `SELECT ... FOR UPDATE` единственной строки `planner_meta`. После захвата проверяет глобальную `revision`, валидирует команду, расширяет предков и вычисляет конфликты. При необходимости возвращает 409, не записывая изменения. Повторное подтверждение использует ту же revision; новая операция другой вкладки приведёт к 409 STALE_REVISION. Поэтому подтверждение не может молча одобрить уже изменившееся расписание. READ использует REPEATABLE_READ для согласованности таблиц. Запись — одна транзакция PostgreSQL; отмена или ошибка сохраняет исходное состояние.

## Чтение

| Метод и путь | Результат |
|---|---|
| GET `/state` | State: `schemaVersion`, `revision`, `tasks`, `checklists`, `items`, `comments`, `entries`, `series`, `timer` |
| GET `/tasks` | Активные задачи; query: `from`, `to` (UTC ISO-инстанты), `q`, `status`, `priority`, `assignee`, `overdue` |
| GET `/stats?from=2026-10-12&to=2026-10-18&zone=Europe%2FMoscow` | План, факт, отклонение, количество, завершённые, `planByDay`, `actualByDay` |
| GET `/backup/export` | Полный State, включая корзину и таймер |

Карточки и списки дочерних ресурсов читаются из `/state`, что обеспечивает одну согласованную версию всего дерева. `from/to` в `/tasks` задают полуоткрытое пересечение; даты `/stats` включительны. Сводка считает количество всех датированных задач, включая потомков, но план — только корней.

## Команды

POST `/api/v1/{resource}/{action}`, `Content-Type: application/json`:

```json
{
  "revision": 7,
  "confirm": false,
  "preview": false,
  "data": {}
}
```

`revision` берётся из последнего State. `preview:true` выполняет расчёт без записи. `confirm:true` разрешает перечисленные предупреждения при той же версии; не отменяет валидацию. Ответ: `{state,conflicts,expanded,warnings,saved}`. В preview/409 поле state содержит предполагаемое состояние, не сохранённое в базе.

| Resource/action | data |
|---|---|
| `tasks/save`, `schedule/save` | `{task: Task, scope: "ONE" или "FUTURE"}`. Новый UUID создаёт задачу; существующий заменяет редактируемые поля. Статус, reparent и расписание обновляются этой же командой. |
| `tasks/delete` | `{id, scope}`: обратимое удаление дерева, блокируется активным/приостановленным таймером ветки |
| `tasks/restore` | `{id}`: восстанавливает задачу и потомков из того же удаления; может потребовать подтверждения конфликтов |
| `tasks/clone` | `{id}`: копия основных полей и чек-листов, без потомков, комментариев и факта |
| `checklists/save` | `{id, taskId, title, sortOrder}` |
| `checklists/delete` | `{id}`: вместе с пунктами |
| `checklist-items/save` | `{id, checklistId, text, done, sortOrder}` |
| `checklist-items/delete` | `{id}` |
| `comments/save` | `{id, taskId, text}`; сервер устанавливает timestamps |
| `comments/delete` | `{id}` |
| `time-entries/save` | `{id,taskId,source,startAt,endAt,workDate,seconds}`; при интервале seconds вычисляет сервер |
| `time-entries/delete` | `{id}` |
| `timers/start`, `timers/resume` | `{id: taskId}` |
| `timers/pause`, `timers/stop` | `{}` |
| `recurrences/save` | `{id,templateId,frequency,zone,weekdays,count,until}`; frequency DAILY/WEEKLY/WEEKDAYS/MONTHLY, weekdays ISO 1–7 |
| `recurrences/delete` | `{id}`; снимает принадлежность задач к серии, не удаляет задачи |
| `backup/import` | `{state: State,mode:"MERGE" или "REPLACE",confirmed:true}` |

Полная структура Task и остальных сущностей — в `frontend/src/model.ts` и `Model.java`. ISO timestamps передаются с `Z`/offset и читаются как Java Instant. Пустые даты — JSON `null`, не пустая строка. Для ручной длительности: startAt/endAt=null, workDate=`YYYY-MM-DD`, seconds>0. В интервальной записи должны быть оба конца, endAt>startAt. TIMER и MANUAL независимы от планового расписания.

Ошибки:

```json
{"code":"VALIDATION","message":"Конец должен быть позже начала; заполните обе даты"}
```

- 400 `VALIDATION`: некорректный запрос/бизнес-инвариант.
- 409 `CONFIRM_REQUIRED`: `details` содержит Result со списком конфликтов, расширенных родителей и предупреждений.
- 409 `STALE_REVISION`: обновить State, проверить изменения и повторить команду.
- 500 `INTERNAL`: транзакция откатилась; подробности только в серверном журнале.

Импорт отвергает неполную верхнеуровневую структуру, неизвестные свойства, неверную schemaVersion, повторяющиеся ID, некорректные ссылки и значения. MERGE намеренно не разрешает коллизии ID: требуется другая копия или явный REPLACE. Операции редактирования ориентированы на доверенного локального пользователя; сеть и многопользовательская авторизация в область применения не входят.
