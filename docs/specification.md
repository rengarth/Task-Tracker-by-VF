# Техническое задание для Codex: локальный персональный планировщик

**Версия:** 1.0  
**Тип:** однопользовательское локальное веб-приложение для планирования времени и задач.  
**Цель:** получить готовое приложение, запускаемое на локальном компьютере в браузере, с базой PostgreSQL и главным представлением «Неделя».

## 0. Инструкция Codex

Реализуй работоспособное приложение целиком, а не только макет интерфейса. Не заменяй реальное хранение заглушками и не ограничивайся демоданными. Сначала исследуй репозиторий и существующее окружение, затем определи план реализации и приступи к коду. При наличии проекта сохраняй его принятые соглашения. Если репозиторий пустой — используй стек ниже. Не удаляй существующие данные или базы. Для запуска предоставь README и скрипт запуска. Избегай необязательных внешних сервисов и платных API. Не спрашивай подтверждение на несущественные детали дизайна: выбирай практичные решения согласно этому ТЗ. Проверяй приложение тестами и сборкой; не заявляй о прохождении проверок, которых не запускал.

## 1. Стек и эксплуатация

- Frontend: React, TypeScript, Vite.
- Backend: Java, Spring Boot, REST API. Версии выбирать совместимые с установленным JDK и актуальными стабильными библиотеками.
- Данные: существующий локальный PostgreSQL, **отдельная новая база** для приложения, например `personal_planner`.
- Миграции схемы — Flyway (либо уже используемая в проекте система миграций). Не использовать автоматическое разрушительное пересоздание схемы.
- Конфигурация подключения через локальный `.env`/переменные окружения (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`); не коммитить пароли.
- Браузерное приложение на `localhost`; не открывать backend наружу по умолчанию. Без облака, внешней авторизации, подключения к интернету и платных сервисов. Исполнитель по умолчанию — «Я»; предусмотреть поле assignee, не строить многопользовательскую систему.
- Один удобный скрипт запуска для Windows (PowerShell) с понятными сообщениями об ошибках и инструкцией первичной настройки PostgreSQL. Предусмотреть режим разработки и production-like локальный запуск. Скрипт не должен тихо устанавливать/запускать PostgreSQL или изменять чужие БД.
- Данные должны оставаться после перезапуска, обновления страницы и перезапуска компьютера.
- Экспорт всех сущностей в JSON, импорт из JSON с проверкой структуры и явным подтверждением режима (слияние/замена); резервная копия базы. Операции импорта должны быть атомарными и не допускать частичного разрушения данных.

## 2. Основной пользовательский сценарий

Пользователь открывает приложение и видит текущую неделю. Создаёт задачи непосредственно в календаре, назначает начало и конец, описывает работу, задаёт приоритет, создаёт подзадачи и чек-листы; перемещает и растягивает временные блоки мышью. Приложение предупреждает о конфликтах расписания, показывает просроченное, позволяет вручную переносить его на новую дату. Пользователь запускает таймеры и вручную вносит фактическое время; смотрит план и факт за период.

## 3. Навигация и календарные представления

### 3.1 Неделя — стартовый и основной экран

- Семь колонок с днями недели (понедельник–воскресенье), вертикальная временная шкала.
- Расположение задач строго по дате/времени; высота пропорциональна длительности, а не фиксированным «слотам». Настройки визуального масштаба/шага сетки 15, 30, 60 минут; шаг сетки не меняет реальные интервалы.
- Навигация «предыдущая/следующая неделя», «сегодня», переход к выбранной дате, подсветка текущего дня и линия текущего времени.
- Сетка суток должна корректно обслуживать все 24 часа, в том числе задачи, пересекающие полночь; можно по умолчанию показывать наиболее используемые часы с прокруткой.
- Создание задачи выделением интервала в пустой области или по кнопке «+».
- Drag & Drop задачи между днями и временами и изменение длительности перетаскиванием нижней границы; поддержать клавиатурный/форменный способ для доступности.
- Задачи с пересекающимися интервалами визуально располагаются рядом, без перекрытия названий целиком.
- Длинные названия обрезаются аккуратно, полная информация доступна по нажатию.
- Дополнительные панели: «Без даты» (бэклог) и сворачиваемая «Просроченные», из которых задачу можно перетащить в расписание.

### 3.2 Месяц

- Классическая календарная сетка дней, задачи внутри ячеек по возрастанию времени начала.
- При нехватке места — «+ ещё N» с просмотром полного списка дня.
- Нажатие задачи открывает карточку, на день — переход в недельный вид.

### 3.3 Год

- 12 месяцев как тепловая карта загрузки по суммарным **запланированным часам** на каждую дату.
- Показывать легенду интенсивности; пустой день отличать от загруженного. Переход по дню в недельный вид.
- Длительность задач, пересекающих полночь, распределяется по фактическим календарным дням.

### 3.4 Произвольный период

- Выбор двух дат (включительно), хронологический список по дням, фильтры и сводка: количество задач, плановые часы, фактические часы, отклонение и завершение.
- Бэклог без даты выводится отдельно, а не искусственно включается в временной диапазон.

## 4. Задача: свойства и действия

Поля:
- ID (UUID или иной стабильный идентификатор), название (обязательно), описание (необязательно, многострочное).
- Исполнитель (по умолчанию «Я»; поле хранится в БД).
- Приоритет — 4 уровня: низкий (синий), обычный (зелёный), высокий (жёлтый), критический (красный); обычный по умолчанию.
- Статус: `PLANNED` («Запланирована»), `IN_PROGRESS` («В работе»), `DONE` («Выполнена»), `CANCELED` («Отменена»).
- Необязательные `startAt`, `endAt` для бэклога; если задача запланирована, оба обязательны и `endAt > startAt`.
- Необязательный `parentId`, системные `createdAt`, `updatedAt`, `completedAt` и порядок сортировки дочерних сущностей.
- Комментарии с текстом и датой создания/изменения, редактирование и удаление.
- Чек-лист(ы) с пунктами (текст, порядок, выполнен/не выполнен); добавить/удалить/редактировать/переставить пункты.
- Список подзадач и их прогресс; визуальная индикация наличия подзадач и чек-листов прямо на карточке календаря.
- Действия: создать, открыть, отредактировать, дублировать, удалить (с подтверждением), перетащить, сменить статус, добавить комментарий/подзадачу/чек-лист, перенести в бэклог.

Внешний вид: приглушённый фон + яркая цветная левая полоска по приоритету; не заливать всю сетку кислотными цветами. В календарной карточке показывать название, интервал, приоритет, значок просрочки, индикаторы чек-листа/подзадач и счётчики `x/y` по мере доступного пространства.

## 5. Подзадачи, вложенность и расширение родителя

- Подзадача — полноценная задача с `parentId`, описанием, статусом, чек-листами, комментариями, временем и собственными учётными сессиями; время указывать необязательно.
- Максимальная глубина дерева — **родитель → подзадача → подподзадача** (2 уровня потомков). Запретить циклы, смену parent на потомка и превышение глубины, в том числе на сервере.
- В календаре первично показывать родительскую задачу. Подзадачи с интервалом, полностью лежащим внутри родителя, показывать в раскрытии родителя, не как отдельные независимые блоки. Подзадачи за пределами родительского интервала должны оставаться доступны в раскрытии и при необходимости через навигацию из списка, но не должны дублировать блоки/часы календаря при автоматическом расширении родителя.
- Когда запланированная подзадача выходит за временные границы родителя, родитель автоматически **расширяется** до `min(старый startAt, startAt дочерних)` / `max(старый endAt, endAt дочерних)`; правило применять транзитивно к предкам. Родителю без расписания при первой датированной подзадаче назначить охватывающий её интервал.
- **Никогда автоматически не сужать** интервал родителя при удалении или сокращении подзадачи. Ручное изменение родителя допускается, но если его дети выходят за новый диапазон — автоматически расширить обратно и сообщить пользователю, почему. Изменение нескольких сущностей должно выполняться транзакционно.
- Родитель и его потомки друг с другом не считаются конфликтующими; также исключить двойное визуальное суммирование плановых часов в сводках (см. п. 10).
- В карточке родителя отображать раскрываемые подзадачи и чек-листы; чек-листы внутри подзадач сворачивать за меню «…», чтобы вложенные детали не заполняли экран.
- Прогресс дочерних элементов рассчитывать, но он **не завершает родителя автоматически**. Родитель переходит в DONE только вручную. Позволить вручную завершить родителя при незавершённых детях с предупреждением и подтверждением; детей не завершать автоматически.

## 6. Пропущенные задачи

- `overdue` — вычисляемый признак, **не отдельный статус**: `endAt < now` и статус не DONE/CANCELED. Не считать просроченными задачи без расписания. Для одинакового момента окончания и «сейчас» просрочка ещё не наступила.
- Показывать `!` непосредственно слева от названия на календаре и в заголовке окна задачи; обеспечить доступный текст/tooltip «Просрочена».
- После перемещения на будущий интервал признак автоматически исчезает; никуда автоматически задачу не двигать.
- Сворачиваемая панель «Просроченные задачи» с переходом к задаче и возможностью Drag & Drop на новую дату; фильтр просрочки доступен в поиске/списке.
- Время для определения просрочки должно обновляться, даже когда пользователь не выполняет действий на странице, и после возвращения на вкладку.

## 7. Коллизии расписания

- Для двух независимых задач A и B конфликт, если интервалы пересекаются по правилу `A.start < B.end && B.start < A.end`. Соприкасающиеся границы (конец одной = начало другой) — **не конфликт**.
- Не считать конфликтом задачи в одной линии «предок–потомок». Для независимых веток сравнивать их корневые календарные блоки, чтобы одно пересечение не выдавалось несколько раз из-за дочерних сущностей.
- Проверять при создании, изменении времени, DnD, растягивании и автоматическом расширении родителя. Сервер — источник истины, проверка обязательна и на backend.
- Показывать предупреждение со списком конфликтующих задач, их временем и ссылками/кнопками «Открыть задачу»; подсвечивать соответствующие блоки.
- **Конфликт — предупреждение, не запрет:** пользователь может отменить операцию или явно подтвердить сохранение с пересечением. Не сохранять молча до выбора пользователя. API должно поддерживать проверку валидации и явное подтверждение конфликтов без гонок при одновременных изменениях.
- После подтверждения сохранять две задачи в календаре рядом, если они пересекаются.

## 8. Бэклог, повторения, фильтры и удобство

- «Без даты» — список незапланированных задач. Можно создавать там задачи, переносить из календаря обратно и перетаскивать в неделю.
- Повторения: ежедневно, по выбранным дням недели, еженедельно, ежемесячно; ограничение по дате окончания или количеству повторов. Редактирование «только этого экземпляра» или «этого и будущих»; удаление аналогично. Исключения не должны теряться после изменения серии. Реализацию recurrence документировать и покрыть тестами. Достаточно простой системы повторений без полноценного внешнего календарного протокола.
- Поиск по названию/описанию, фильтры по статусам, приоритетам, просрочке, исполнителю.
- Быстрое дублирование задач (по умолчанию без комментариев и без фактических временных сессий); шаблоны типовых задач, если остаются ресурсы после основного функционала.
- Undo последнего перемещения/изменения длительности/удаления в пределах текущей сессии UI; если Undo сложен для удаления, допустимо «корзина/восстановление», но без необратимого удаления одним кликом.
- Горячие клавиши для создания/сохранения/отмены по стандартным привычным сочетаниям, без перехвата ввода в текстовых полях.
- Адаптивный desktop-first интерфейс. Основной целевой браузер — современный Chromium на Windows; при узких экранах допустима горизонтальная прокрутка сетки.

## 9. Таймер, сессии работы и учёт факта

- У задачи любого уровня можно запустить таймер Start, Pause, Resume, Stop. Разрешён только **один активный таймер на весь планировщик**. При попытке запустить другой предложить приостановить предыдущий и затем запустить новый; не терять уже учтённое время.
- Время считать по сохраняемым меткам времени на сервере, а не только локальным JS-счётчиком. Перезагрузка страницы и рестарт приложения не должны терять активную/приостановленную сессию.
- Хранить отдельные записи фактической работы (time entries) с задачей, источником `TIMER`/`MANUAL`, датой/временем старта и окончания либо длительностью для ручного ввода. Разрешить редактировать и удалять записи; проверять длительность > 0 и корректность интервалов.
- Плановое время и фактическое время **независимы**: фактический учёт никогда не сдвигает задачу и не изменяет плановую длительность.
- Фактическое время родителя = собственные сессии + все сессии потомков, рекурсивно. Каждая запись входит в агрегат **ровно один раз**. В UI показывать собственное и суммарное время для прозрачности.
- Для таймера не допускается параллельных активных сессий; ручные записи могут быть добавлены независимо. Предусмотреть валидацию и явно описать, что ручные записи за пересекающиеся интервалы не объединяются автоматически (это разные записи; пользователь отвечает за корректность ручного ввода).
- Сводка по периоду: запланированные часы, фактические часы, отклонение, количество задач и завершённых задач. При группировке по дням разбивать записи фактического времени по календарным дням; записи ручной длительности без времени привязывать к указанной пользователем дате работы.

## 10. Правила расчётов и пограничные случаи

- Все серверные метки времени хранить как инстанты с корректной временной зоной (например, `timestamptz` / UTC), а даты/время в интерфейсе отображать в настроенной локальной зоне; по умолчанию брать зону устройства и предоставить настройку. Не захардкодить UTC как локальное время интерфейса. Учитывать переходы на зимнее/летнее время.
- Продолжительность интервала = `endAt - startAt`. Для недельной/годовой статистики не суммировать родителя с его дочерними задачами второй раз; плановая длительность дерева в календаре — длительность **корневой** запланированной задачи. При наличии независимых корневых задач с пересечениями суммировать их длительности как плановые трудозатраты, не как уникальное занятое время. При необходимости отдельно показывать уникально занятую долю суток, но не смешивать метрики.
- Для родительской задачи с собственным плановым интервалом и подзадачами этот интервал включает все детские интервалы. Изменение времени подзадачи может растянуть родителя и вызвать предупреждение о конфликте: показывать итоговый диапазон *до сохранения*, сохранять транзакционно после подтверждения.
- Для задач без дат нельзя считать просрочку и нельзя запускать проверку календарных конфликтов.
- Чек-лист хранить отдельно от подзадач; выполнение пункта чек-листа не создаёт новую календарную запись.
- При удалении родителя подтверждать каскадное удаление его потомков, чек-листов, комментариев и записей времени либо поддерживать безопасное восстановление в корзине. Не оставлять осиротевшие строки.
- Для завершения родителя не менять статусы детей автоматически. Переход DONE → PLANNED должен сохранять историю времени.
- Если таймер работает у задачи, запретить её окончательное удаление до остановки таймера (либо явно остановить в подтверждённой транзакции).
- Возможны очень длинные и пересекающие сутки задачи: календарь должен рисовать сегменты на каждом затронутом дне, не дублируя сущность и время.

## 11. UI/UX и требования к качеству

- Интерфейс на русском языке. Чистый, неброский, удобный для многократного ежедневного использования; информативность важнее декоративности.
- Карточку редактирования удобно открыть с недельного экрана; поля название, статус, приоритет, исполнитель, время, описание, комментарии, подзадачи, чек-листы, план/факт, таймер.
- Ошибки показывать человеческим русским текстом, ввод валидировать, не терять несохранённые изменения случайным закрытием.
- Выполнение задач не должно приводить к исчезновению блока без явного фильтра; завершённые визуально отличаются.
- Асинхронные операции должны показывать состояния сохранения/ошибки; UI не должен объявлять успешное сохранение до ответа сервера.
- Проверить доступность: управление формами с клавиатуры, фокус, не полагаться исключительно на цвет, подписи к иконкам, контрастность.

## 12. API и данные

Предусмотреть версионированное REST API `/api/v1` с единым форматом ошибок и валидацией. Набор ресурсов (точный контракт задокументировать OpenAPI или README):

- `tasks`: CRUD, выборка по диапазону, фильтрация, клонирование, обновление статуса, reparent с проверкой циклов.
- `checklists` / `checklist-items`: CRUD и изменение порядка.
- `comments`: CRUD.
- `schedule`: предварительная проверка изменения интервала и его влияния на родительское дерево, получение конфликтов, подтверждённое сохранение.
- `recurrences`: CRUD шаблона/серии и исключений для отдельных экземпляров.
- `time-entries` / `timers`: старт/пауза/возобновление/остановка, ручные записи, история и корректировки.
- `stats`: расчёт метрик по диапазону без двойного подсчёта времени.
- `backup/export` и `backup/import`.

Модели и связи разнести по таблицам. Нужны индексы по `start_at`, `end_at`, `parent_id`, `status`, `task_id` в комментариях и time entries; внешние ключи и проверки целостности. Для важных операций использовать транзакции; для конфликтующих одновременных изменений — блокировки/версионирование по необходимости. Приводить даты/таймзоны к единым правилам. Не хранить секреты в коде.

## 13. Тестирование и критерии приёмки

Codex должен реализовать автоматические тесты ключевой бизнес-логики (предпочтительно unit + интеграционные тесты с PostgreSQL или Testcontainers) и проверить сборку frontend/backend.

Минимальные сценарии приёмки:

1. Приложение стартует локально и работает после обновления страницы; данные хранятся в отдельной PostgreSQL БД.
2. Создание задачи на понедельник 14:00–16:00 показывает блок соответствующей высоты; редактирование на 14:00–17:30 меняет высоту без потери данных.
3. Перенос в другой день и изменение нижней границы задачи сохраняются после перезагрузки.
4. Независимая задача 15:00–16:00 конфликтует с 14:00–17:30; предупреждение содержит кликабельную задачу, отмена оставляет исходные данные, явное подтверждение сохраняет конфликт.
5. Две задачи 14:00–15:00 и 15:00–16:00 **не конфликтуют**.
6. Подзадача родителя 14:00–16:00 со временем 15:00–18:00 расширяет родителя до 14:00–18:00; уменьшение/удаление ребёнка не сужает родителя.
7. Расширение родителя через изменение подзадачи проверяет конфликты с независимыми задачами до сохранения.
8. Отношение родитель–потомок не выдаётся как конфликт; циклы в дереве отклоняются.
9. Закрытие всех чек-листов и подзадач не завершает родителя; ручное DONE работает даже при незавершённых детях после предупреждения.
10. Прошедшая невыполненная задача имеет `!` в сетке и заголовке; отображается в «Просроченных» и может быть вручную перенесена; выполненная/отменённая не просрочена.
11. Бэклог содержит задачу без дат; перетаскивание на неделю назначает ей интервал.
12. Неделя, месяц, год и произвольный период показывают согласованные данные. Годовой heatmap корректно распределяет часы задачи через полночь.
13. Запуск таймера задачи A и попытка запустить таймер B предлагают приостановить A; после перезапуска таймер/сессии корректны.
14. Записи ручного времени корректируются; суммарный факт родителя = свои записи + записи всех потомков без повторного учёта.
15. В сводке план и факт различаются; дочерние плановые интервалы не добавляются второй раз поверх родительского.
16. Повторяющаяся задача генерирует экземпляры; редактирование одного экземпляра не меняет всю серию; «этот и будущие» работает как документировано.
17. Экспорт в JSON и импорт в чистую тестовую базу восстанавливают задачи, иерархию, чек-листы, комментарии, повторы и учёт времени.
18. Некорректные интервалы, невалидные ссылки на родителя и пустое имя задачи отклоняются сервером с понятными ошибками.
